# Taste ledger

The user's taste, built from their reactions. It has two halves that are used in opposite ways:

1. **Rules** come from what the user rejected or asked for ("get rid of the legend", "I wish it played itself"). They are constraints: pass or fail, checked on every set before it's shown.
2. **What landed** comes from what the user liked. It is a *quality bar*, never a rule and never a template. It answers "is this as good as that was?", not "does this look like that?". A liked variant's form (its ground, its kind of figure, its layout) must never be checked for, asked for or reused. Doing so collapses range into one house style, the very thing this skill exists to prevent.

Why the split: a dislike removes one option and leaves every other one open. A like, enforced, removes every option but one.

Update this file only when the user explicitly asks. When they do:
- A rejection or request → a rule (or new evidence on an existing rule).
- Praise → an entry under What landed, written as the quality underneath it, with its surface listed as "don't reuse".
- If the user approves something that breaks a rule, loosen the rule and record the exception as evidence.

How to write a rule:
- **Rule:** one line a stranger could check on a screenshot. "No legend in the figure's corners", not "keep it clean".
- **Check:** what to look at to decide pass or fail.
- **Evidence:** date, brief, and what the user said, in a few words. Add new evidence to an old rule rather than writing a near-duplicate.

Rule format:

```
**F1. Short rule name.** One line a stranger could check on a screenshot.
- Check: what to look at to decide pass or fail.
- Evidence: date, brief, what the user said.
```

What-landed format:

```
**Variant name, date.** What the user said.
- The quality: the thing underneath that made it work.
- Don't reuse: its surface (ground, kind of figure, layout).
```
